# 项目简历亮点生成

基于可验证证据提炼项目经历，先写用户真正做过的工作，再写有技术深度的实现。默认生成中文技术简历内容，不输出无法在面试中解释的包装话术。

## 开始前

确认项目路径可读。用户提供了目标岗位、个人角色、已有简历或明确贡献时直接使用；缺少这些信息时仍可扫描项目，但将“仓库具备的能力”与“用户确认的个人贡献”分开，不能自动把仓库全部实现写成个人职责。

需要判断证据可信度、改写句式或量化规则时，读取 `references/writing-rules.md`。生成最终内容时，套用 `assets/project-resume-template.md`，按实际情况删除空栏目。

## 扫描项目

1. 查找并遵守项目中的 `AGENTS.md`。
2. 扫描 README、构建文件、依赖清单、配置文件、启动入口、核心业务目录、测试及部署文件。
3. 忽略 `node_modules/`、`target/`、`dist/`、`build/`、缓存和生成产物。
4. 识别项目解决的问题、目标用户、核心流程、架构形态和主要技术栈。
5. 查找能体现难度的实现：并发、缓存、一致性、异步、流式响应、工作流、权限、安全、限流、监控、容错、性能和可扩展性。
6. 必要时查看 Git 日志和 blame，以辅助判断改动范围；Git 作者不明确等于当前用户时，不据此断言个人所有权。
7. 为候选条目记录证据文件或符号，避免只根据 README 宣传语写简历。

## 确认个人贡献

- 用户明确说明自己完成的内容，作为个人贡献候选，但仍检查代码是否支持技术细节。
- 代码只能证明“项目存在该实现”，不能单独证明“用户本人完成”。
- 无法确认个人归属时，先给出“待确认候选项”，询问用户选择实际做过的内容。
- 不把教程原有功能、团队整体成果或他人提交直接写成“本人负责”。

## 组织内容

### 项目描述

用一至两句话说明项目服务对象、解决的问题、核心能力和最终形态。不要堆砌框架名，不写“对标大厂”“行业领先”等无证据宣传语。

### 技术栈

只保留与主要工作和技术亮点直接相关的技术；按语言/框架、AI 或业务中间件、存储、基础设施组织为一行。

### 主要工作

以用户真实承担的工作为主体，默认四至六条。每条严格使用：

```text
概括：具体动作 + 关键实现 + 产出或作用
```

概括应为四至十个汉字的能力标签，例如“代码生成链路”“AI 工具体系”“可视化编辑”。具体细节回答“做了什么”，不要只罗列技术名。

### 技术亮点

选择三至五个最能体现难度和取舍的点。每条严格使用：

```text
概括：技术问题 + 方案/机制 + 可验证结果或价值
```

技术亮点回答“为什么难、如何解决、带来什么价值”，不得与主要工作原句重复。

## 改写已有简历

1. 保留能够被代码或用户经历支持的事实。
2. 将缺少概括的条目补成“概括：具体细节”。
3. 将过长条目拆分，将重复条目合并。
4. 把“使用了某技术”改成“为解决某问题，使用某机制完成某结果”。
5. 删除无法解释的术语、虚假量化和与目标岗位无关的边缘功能。
6. 对未确认内容加“待确认”，不要静默润色成既定事实。

## 输出要求

- 默认只输出可直接放入简历的正文，以及必要的“待确认事项”。
- 所有“主要工作”和“技术亮点”条目都必须且只能包含一个首个中文冒号，冒号前是概括，冒号后是具体细节。
- 一条只表达一个核心主题，避免一条塞入多个无关功能。
- 不使用“精通”“极大提升”“高并发”等无法证明的空话。
- 百分比、耗时、吞吐量、准确率等数字必须来自测试、监控、报告或用户明确确认；否则改写为定性价值。
- 输出完成后，逐条检查用户能否根据代码说明背景、方案、取舍和结果。

## 自检

确认以下事项后再交付：

1. 项目描述以业务价值为主，技术栈没有喧宾夺主。
2. 主要工作描述个人真实动作，技术亮点描述难点与方案。
3. 每条均符合“概括：具体细节”。
4. 技术名称、模块关系和实现机制与仓库一致。
5. 没有把仓库能力自动归为个人贡献。
6. 没有编造量化指标、用户规模或线上效果。
