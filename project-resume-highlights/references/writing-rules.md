# 项目简历写作与证据规则

## 证据优先级

按以下顺序判断是否能写进简历：

1. 用户明确确认的个人工作，并能指出代码、文档或交付物。
2. 用户身份可确认的 Git 提交、PR、Issue 或设计文档。
3. 仓库中可验证的实现，但个人归属仍需确认。
4. README、需求说明或截图中的项目能力，仅能作为扫描线索。
5. 推测、宣传文案和模型常识，不作为简历事实。

项目存在某项功能不等于用户亲自实现。证据不足时使用“候选项/待确认”，不要使用“负责、主导、设计并实现”等归属词。

## 两类条目的区别

### 主要工作

回答“我具体承担了什么”。推荐结构：

```text
业务或模块概括：使用关键动作完成核心实现，说明交付物或作用。
```

示例：

```text
代码生成链路：设计统一生成入口与类型路由，串联模型调用、流式解析和文件保存流程，支持多种工程生成模式。
```

### 技术亮点

回答“技术难点是什么，方案为什么有效”。推荐结构：

```text
技术能力概括：针对具体问题采用关键机制，说明原理、取舍和可验证价值。
```

示例：

```text
多级缓存优化：使用 Redis 保存分布式会话记忆，并通过 Caffeine 缓存 AI Service 实例，兼顾跨实例数据共享与本地访问性能。
```

## 概括标签规则

- 使用四至十个汉字。
- 优先使用“对象 + 能力”或“技术 + 目标”，如“工作流编排”“接口限流治理”“模型调用监控”。
- 不使用“负责开发”“相关工作”“技术优化”等空泛标签。
- 同一份项目经历中避免近义标签重复。

## 具体细节规则

一条内容优先包含以下三项中的两至三项：

1. 场景或问题：为什么需要做。
2. 动作或机制：具体如何实现。
3. 结果或价值：带来什么可验证作用。

不要把依赖列表写成亮点：

```text
错误：缓存优化：使用 Redis、Caffeine、Spring Cache。
正确：缓存优化：针对重复创建 AI 服务实例的问题，引入 Caffeine 本地缓存并设置回收策略，减少实例初始化开销。
```

## 量化规则

仅在存在以下证据时使用数字：

- 基准测试或压测报告。
- 监控平台数据。
- 测试用例与可复现测量。
- 用户明确确认的线上数据。

无法验证时使用定性描述：

```text
不要写：接口性能提升 60%。
可改为：减少重复远程调用，降低核心查询链路的响应开销。
```

## 技术深度检查

每个技术亮点至少能继续回答三个面试问题：

1. 原方案或业务痛点是什么？
2. 为什么选择该方案，替代方案有哪些？
3. 如何验证效果，存在哪些边界或风险？

无法回答时，降低措辞强度或删除该条目。

## 常见问题

- 将团队项目全部功能写成个人职责。
- 只列技术名，没有问题与动作。
- 主要工作和技术亮点重复。
- 每条过长，包含多个不相关主题。
- 使用未经证实的百分比、并发量或准确率。
- 为了“高级感”堆砌源码中不存在的架构术语。
