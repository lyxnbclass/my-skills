# 工作日报生成

将用户提供的事实整理为简洁、职业、可直接发送的日报。默认输出纯文本，避免复杂表格和多余解释。

## 处理流程

1. 提取日期、项目、今日完成、进行中、问题或风险、需要协助、量化结果和明日计划。
2. 合并重复事项，按项目或工作主题组织内容。
3. 将事项改写为“动作 + 结果 + 影响”；用户未提供结果或影响时只写已有事实。
4. 明确区分“已完成”“进行中”和“计划中”，不得改变状态。
5. 检查敏感信息、内部地址、密钥、客户隐私和未经确认的数据；发现时提醒用户脱敏。
6. 输出适合直接复制到飞书或企业微信的日报。

## 信息不足时

- 用户提供了足够事实时，直接生成，不重复追问。
- 缺少某一栏目时，省略该栏目或写“暂无”，不要编造内容。
- 缺少决定日报真实性的关键信息时，先生成可用草稿，再在末尾列出不超过三个待补充问题。
- 用户只说“帮我写日报”但没有提供任何工作记录时，请其提供今日工作、问题风险和明日计划。

## 写作规则

- 使用客观、简洁、职业的中文。
- 优先写具体动作与可验证结果，避免“积极推进”“持续跟进”等空泛表达。
- 保留用户提供的数字、时间、状态和专有名词，不擅自修改。
- 不夸大个人贡献，不把团队成果全部归于个人。
- 风险项写清“问题、可能影响、当前动作或需要协助”。
- 默认每条控制在一至两句话；除非用户要求，不展开技术实现细节。
- 用户指定“领导版”“简短版”“技术版”或其他格式时，服从用户要求。

## 默认输出格式

```text
【工作日报｜YYYY-MM-DD】

一、今日完成
1. …
2. …

二、进行中
1. …

三、问题/风险及需协助事项
1. …
（没有时写“暂无”）

四、明日计划
1. …
2. …
```

## 可选风格

### 简短版

适用于日常打卡，仅保留“今日完成、问题风险、明日计划”，总长度尽量控制在 200 至 400 字。

### 领导版

突出结果、价值、风险和需要决策或协调的事项，减少实现细节。

### 技术版

保留模块、接口、缺陷、测试、性能等必要技术信息，但仍以结果和影响为主。

## 示例

输入：

```text
今天完成登录接口联调；订单查询从2秒优化到300毫秒；支付模块开发中；
第三方支付测试环境不稳定；明天继续支付联调并准备测试。
```

输出：

```text
【工作日报｜YYYY-MM-DD】

一、今日完成
1. 完成登录接口联调，验证登录主流程可正常运行。
2. 完成订单查询接口性能优化，响应时间由约 2 秒降低至约 300 毫秒。

二、进行中
1. 支付模块开发中，正在推进核心流程实现与联调准备。

三、问题/风险及需协助事项
1. 第三方支付测试环境稳定性不足，可能影响联调进度；需协调确认稳定的测试时间窗口。

四、明日计划
1. 继续推进支付模块联调。
2. 准备支付模块测试事项。
```

## 输出前检查

确认日期、数字、项目名称和完成状态与用户输入一致。删除重复内容、草稿说明和不必要的解释，只保留可直接发送的日报正文；存在待补充信息时放在正文之后。
